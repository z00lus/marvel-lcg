## Overview

The engine follows a **3-layer architecture**:

```
┌─────────────────────────────────────────────┐
│                  main.py                    │
├─────────────────────────────────────────────┤
│                                             │
│  ┌─────────────────────────────────────┐    │
│  │           game/ (Logic)             │    │
│  │  World, Player, Card, Ability,      │    │
│  │  Effect, Phase, Scene, Deck         │    │
│  ├─────────────────────────────────────┤    │
│  │           engine/ (Platform)        │    │
│  │  Device, Controller, WebServer,     │    │
│  │  Config, Log, FileManager, Task     │    │
│  ├─────────────────────────────────────┤    │
│  │           core/ (Foundation)        │    │
│  │  Types, Debug, Math, Tracker        │    │
│  └─────────────────────────────────────┘    │
│                                             │
└─────────────────────────────────────────────┘
```

- **core/** — Foundational utilities, type system, debug tools
- **engine/** — Platform layer: device management, networking, controllers, file I/O
- **game/** — Game logic: cards, abilities, players, world, phases, effects

### Card Model

The card system has 3 layers:

```
Paper (static)          CardFace (runtime)         Card (dynamic)
├── card_id             ├── attributes             ├── state
├── pic_id              ├── components             ├── visible
├── type                ├── abilities              ├── area
├── name                ├── owner                  ├── face
├── traits              └── methods                └── back_faces
└── desc
```

**Paper** — Static card data from JSON/Python files. Loaded once at startup.

**CardFace** — Runtime representation of a card face with attributes (attack, health, cost, etc.) and components (counters, tokens, statuses, inventory).

**Card** — Dynamic card object that moves between zones, tracks state, and manages visibility.

### Ability System

Abilities are the core of card logic.

**AbilityType** defines the timing/priority of an ability:

```
TimingPriority:
  Rule → Constant → Status → ForcedInterrupt → Interrupt →
  Boost → ForcedResponse → Response → Normal → Consequential → End
```

**Ability** contains:
- `type` — AbilityType (when it triggers)
- `when` — Message type (what event it listens to)
- `conditions` — List of condition functions
- `selectors` — Targeting rules
- `cost_funcs` — What the player must pay
- `operation` — What happens when the ability resolves

### Message System

Messages broadcast game events to all cards in play:

```python
class Message2:
    WhenPlayerInTurn            # During player's turn
    WhenPlayerTurnBegin/End     # Turn boundaries
    AfterCardEnterPlay          # Card entered play
    WhenUnitWouldTakeDamage     # Damage prevention window
    WhenUnitWouldAttack         # Attack interruption window
    WhenCalculateAttackDamage  # v1.8 step: ATK/boost modifiers, then DEF
    WhenPlayerRevealCard        # Encounter card revealed
    WhenCardRevealed            # After reveal
    WhenUnitBeDefeated          # Unit defeated
    AfterUnitAttackUnit         # After attack
    WhenObligationGiveToPlayer  # Obligation dealt
    # ... many more
```

Enemy attacks use `WhenCalculateAttackDamage` as the sole Rules Reference 1.8
Calculate Damage boundary. Its `attack_damage` is the modified ATK plus boost
icons before defense; `calculated_damage` applies the declared hero's DEF once
and is passed to the later damage instance. Boost abilities resolve before this
message and any damage they deal remains a separate, non-attack damage event.
The former `WhenRecalculateAttackDamage` hook was migrated to this message and
removed; there is no second runtime calculation path.

## Data Flow

### Startup

```
main.py
  → Engine.Initialize()
    → ConfigVariables.Initialize()    # Parse args + launch.json
    → JobManager.Initialize()         # Thread pool
    → TaskManager.Initialize()        # Async threads
    → UserInfo.Initialize()           # User fingerprint
    → TransText.Initialize()          # Translations
    → ImageCreator.Initialize()       # Placeholder images
    → CardsDB.Initialize()            # Load card database
    → Editor.Initialize()             # Card editor (dev mode)
    → DeviceManager created           # Web or Keyboard
    → Game(statistics, device_manager)
```

### Game Session

```
Game.GameRun()
  → state.WaitUntilGameStart()        # Wait for new game command
  → session.NewGame(descriptor)       # Create scene
    → SceneLoader.NewScene()          # Build world from scenario + heroes
  → GameSetup()
    → world.Initialize()              # Setup players, decks, phases
    → ControllerManager.Setup()       # Connect devices
  → GameLoop()
    → world.OnGameLoop()              # Run phase logic
      → Phase loop: Player → Villain → End
  → SetGameOver()
  → (loop back to WaitUntilGameStart)
```

### Input Processing

```
User action (click/keypress)
  → WebDevice/KeyInput receives input
  → DeviceManager.WhenInput()         # Notify waiting controller
  → Controller processes input
  → Game logic updates
  → World render
  → DeviceManager.AfterSync()         # Notify clients to sync
```

### launch.json

Create `launch.json` in the project root:

```json
{
    "device": "web",
    "port": 2345,
    "editor": true,
    "debug": false
}
```

For a played card, `EventManager.FilterAvailableEffects()` is only a UI
preflight that decides which options can be displayed. The normative Rules
Reference 1.8 initiation path begins in `PlayerAction.ResolveEffect()`:

1. Move the declared card faceup to the player's processing area. It is on the
   table, but is not in play.
2. `EffectChecker.CheckPlayInitiation()` checks play/form restrictions, legal
   targets, and payable costs in that state. Its result is cached for this
   initiation, so a form change during payment does not reopen step 2.
3. `EffectChecker.CheckBeforeActive()` validates the chosen targets and payment.
   Selected resource effects and simultaneous allocations are validated before
   any resource card is spent.
4. `ClassCard.Play()` pays additional costs and opens the would-play/play
   message windows before resolving the card.

If steps 2-4 fail before the play commences, a card moved to processing solely
for that declaration returns to its source area. Cards that were already in a
processing area remain subject to their caller's existing "play it, otherwise
discard it" handling. Because the placement, checks, payments, and return are
normal modeled operations, replay and undo observe the same deterministic
sequence.

## Extension Points

### Adding a New Device Type

1. Create a new class inheriting from `Device`:

```python
class MyDevice(OutputDevice, InputDevice):
    def IsConnect(self) -> bool: ...
    def IsSyncReady(self) -> bool: ...
    def IsInputReady(self) -> bool: ...
    def Render(self) -> None: ...
```

2. Create a `DeviceManager` subclass:

```python
class MyDeviceManager(DeviceManager):
    def CreateDevices(self, controller) -> Tuple[OutputDevice, InputDevice]:
        return MyDevice(controller, self), MyDevice(controller, self)
```

3. Register in `Engine.Initialize()`:

```python
if DEVICE.value == "my_device":
    from engine.device.manager.my_device.manager import MyDeviceManager
    device = MyDeviceManager
```

### Adding a New Ability Type

1. Add the type to `AbilityType` enum in `game/ability/ability_type.py`
2. Add corresponding flags class in `AbilityTypeFlags`
3. Add timing priority mapping
4. Create a factory method in `AbilityFactory`

### Adding a New Card Type

1. Create a new class inheriting from appropriate base:

```python
class MyCardType(CardFace):
    # Define attributes and components
    pass
```

2. Register in `game/card/face/__init__.py`
3. Add type mapping in `Paper.GetType()`

### Adding a New Phase Step

1. Add phase name to `PhaseName` in `game/world/phase.py`
2. Add phase logic in `World.OnGameLoop()`
3. Update phase transitions
